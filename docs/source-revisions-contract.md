# Source Revision Metadata: S1a Candidate

Status: provisional downstream implementation contract, October 19, 2026. Base `4e565333a3549b75fae7b9ae814b25b152a2453e`. No upstream architectural approval, release, migration or deployment is claimed. This is the first independently reviewable part of S1; extraction/correction lineage is S1b. Neither requires upstream to accept the complete source/policy stack.

## Interface And Identity

Extend the existing `MediaStore` with `register_source_revision(asset_id, *, revision_key, content_hash, representation="original-bytes", byte_size=None, predecessor_revision_id=None, archive_locator=None)`, `get_source_revision(revision_id)` and `list_source_revisions(asset_id, *, limit=100, offset=0)`. Registration returns a small `SourceRevisionWrite(revision_id, status)` result with `created` or `unchanged`. Conflicting immutable fields under the same key raise `ValueError` without updating prior records. Listing is deterministic by registration time/ID, capped at 1,000 rows per request; offset is a nonnegative SQLite integer. There is no implicit latest selection.

The caller supplies a stable, asset-local `revision_key` identifying a revision event, not a location. IDs are deterministic from a versioned encoding of asset ID and revision key. Retries return the same ID; independent events may carry identical byte hashes. Hashes are validated SHA-256 hex digests, normalized to lowercase. This API records an asserted digest, not independent verification. It does not accept a verification claim. S2 will define resolver verification evidence separately.

Source IDs and legacy content-hash semantics remain unchanged. A new revision does not overwrite the asset's earlier hash, URI, moments or derived memories. A predecessor, when supplied, must already exist for the same asset; branching is permitted and there is no implicit latest pointer. Reversion to older bytes is a distinct event if it has a different key. Location changes belong to asset/reference handling, not mutation of an existing revision. `archive_locator` is an optional stable external handle captured with the revision, not an instruction to open a path.

## Storage And Transactions

The additive `media_source_revisions` table contains revision ID, parent asset, revision key, content hash, representation, optional byte size, optional predecessor, optional archive locator, asserted-digest status and UTC registration time. The revision ID and asset/key pair are unique; an asset lookup index supports bounded parent lookup. There are no content, excerpt, BLOB, vector or arbitrary metadata columns. String fields are bounded and known inline/executable `data:`/`javascript:` locators are rejected. This is not a document-storage interface or a complete resolver safety policy; S2/S3 still define supported references, authorization and aggregate retention budgets.

Create the table/index lazily inside the explicit registration operation. Ordinary `MediaStore`/`BeamMemory` construction and missing-table revision reads do not add revision schema. This avoids an automatic migration in legacy stores merely because the candidate source is installed. When there is no outer transaction, registration first obtains SQLite write intent with `BEGIN IMMEDIATE`, before any schema reads, then commits or rolls back its own transaction. A savepoint covers DDL, parent/predecessor validation, insert and idempotency comparison. An already-open caller transaction is never committed or rolled back wholesale by this method; SQLite-level catastrophic errors can nevertheless abort a transaction themselves. Native contention may propagate from a caller-owned read snapshot; the method does not silently restart the caller's transaction. Concurrent workers use independent connections, not one shared connection across threads. No schema-level foreign keys are introduced, matching the existing MediaStore application-integrity convention.

No backfill occurs. Existing hashes are not promoted to verified revisions and timestamps are not invented for them. Reopening or retrying an interrupted registration is safe. Old callers continue to see their existing asset/moment data; this candidate does not change legacy reads to mean the latest revision. Revision history has no automatic deletion/retention/export contract in S1a; raw owner-mode database modifications can invalidate references, as with existing media tables. These lifecycle surfaces require subsequent explicit design and coverage.

## Acceptance And Limits

Use only synthetic, disposable stores. Cover stable IDs, repeated registration, immutable-field conflicts, same-URI changed bytes, identical bytes in distinct revision events, predecessor validity, legacy IDs/reads, absence of original content storage, no source fetch or model/embedding calls, optional-table reads without mutation, outer-transaction preservation, injected DDL/insert failure and retry, reopen persistence, and concurrent independent connections.

This adds no CLI/MCP/Hermes tool, auto-ingest, resolver, extraction correction, embedding, current-revision view, policy activation or migration of existing banks. A source digest is not authorization, a timestamp is not verification, and this module is not a security boundary against raw database owners. Full A/B source and policy scenarios remain unqualified. Version/changelog handling and upstream API/schema acceptance must be settled before an upstream PR; do not silently bump a development release or claim maintainer consent.

The dependent [S2a verification candidate](source-verification-contract.md) adds an explicit bounded byte observation through a caller-supplied resolver. It leaves registration status asserted and immutable; it does not retrofit ordinary recall, persist verification events or authorize future evidence expansion.
