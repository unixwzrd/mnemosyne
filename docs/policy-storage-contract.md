# Prepared Policy Catalog: P1b Candidate

Status: provisional downstream contract, October 19, 2026, based on P1a `ffc8416ffd9b1bf7c9ee6f46b2c51eddb77ad10f`. This adds optional indexed metadata and a durable preparation marker, not protected operation or activation. No upstream architecture approval, release, migration of live data or deployment is claimed. Definitions and bindings are owner-mode metadata APIs, not authorized recall APIs.

## Interface And Schema

`PolicyStore(conn)` requires an explicitly supplied SQLite connection and never opens a default database, changes the row factory, initializes native memory tables or mutates schema in its constructor. `get_domain()` returns a `PreparedDomain` or None. `prepare(domain_id)` explicitly creates the complete catalog and its singleton versioned domain marker in one transaction, returning that domain; repeating the same request is unchanged. A different domain identity, incomplete catalog, unsupported schema/contract version or non-prepared marker is refused, never silently repaired or downgraded. There is no activate/deactivate/reset method or protected-mode parameter.

The five optional tables are `policy_store_state`, `policy_definitions`, `policy_levels`, `policy_bindings` and `policy_binding_terms`. The marker records schema version 1, P1 contract version 1 and mode `prepared`. Definitions have immutable policy ID/version with normalized ordered classification levels. Bindings have deterministic domain/record identity, native record kind/ID, policy ID/version, classification, classification source, owner, optional tenant, optional paired context/epoch and UTC registration time. Compartments, audiences, purposes and overlays are normalized term rows with a reverse dimension/value/binding index. Policy classification/owner/tenant indexes permit subsequent SQL candidate restrictions; no policy-retrieval implementation is supplied here. No opaque JSON policy, full document, content, vector or BLOB column is added. Existing native tables, IDs, `user_version`, PRAGMA settings and configuration are unchanged.

`register_definition(PolicyDefinition)` requires preparation, preserves immutable vocabulary and returns `created` or `unchanged`; a reused ID/version with changed levels is a conflict. `get_definition(policy_id, version)` returns the typed definition or None. `bind(record_kind, record_id, MemoryPolicy)` requires a registered matching definition and an existing native parent; it returns `PolicyBindingWrite(binding_id, status)`. `get_binding(record_kind, record_id)` returns `PolicyBindingRecord` or None. Missing-catalog reads return empty results without migration. One immutable initial binding per native record is allowed; an identical retry is unchanged and any changed restriction conflicts. Reclassification/revocation/history updates are P3, not an overwrite API in this slice.

`RecordKind` is an explicit enum for `working_memory`, `episodic_memory` and `canonical_facts`. Working/episodic IDs are bounded strings; canonical IDs must be positive SQLite integers. Dynamic table names come only from this fixed enum; supplied identifiers are bound parameters. Media, graph/fact derivatives, legacy-mirror records and other targets remain unsupported rather than implicitly bound. Existing bindings can outlive native parent deletion for provenance, but a new/retried bind requires a surviving parent. P3 must handle all lifecycle transitions before protected activation. No automatic propagation to a different tier, derivative, export or cache is implied.

## Compatibility And Interpretation

An unconfigured legacy database receives no policy schema from ordinary opens/reads/writes, even with this source installed. Preparation never classifies or backfills existing rows. Bound metadata does not cause existing BEAM, canonical, vector, lexical, graph, MCP or Hermes paths to authorize or deny a record. An unchanged old client can still read/write prepared stores and ignores the metadata; this is expected legacy compatibility, not safe downgrade from a protected store. A marker is not a security boundary. Actual protected-domain activation and universal old/incompatible-client refusal require later P2-P4 enforcement and remain unavailable.

For future enforcing queries, compartments express required memberships (empty means no extra compartment restriction); audiences and purposes must be explicitly eligible, with an empty set not granting access. No label has wildcard semantics. Owner/tenant and overlay restrictions are independent of classification. The catalog preserves all supplied overlay labels without interpreting or dropping them; P2 must refuse unsupported restrictions before any protected path is offered. These semantics do not affect legacy retrieval now. Policy bindings are security metadata, not authentication or provenance verification.

Use native transactional DDL and bounded per-record writes. Method-owned writes acquire `BEGIN IMMEDIATE` before schema reads and use a savepoint; success/failure finalizes with SQL COMMIT/ROLLBACK. Caller-owned transactions are preserved, including explicit Python sqlite3 autocommit modes. Snapshot reads use savepoints and leave no owned transaction open. No executescript, implicit caller commit, global foreign-key change or destructive migration is used. SQLite errors may propagate; incomplete/unsupported catalog states are content-free `PolicyStoreError` refusals. A catastrophic SQLite error may itself abort a caller transaction. Independent connections are the supported concurrency boundary. Savepoint behavior follows [SQLite documentation](https://www.sqlite.org/lang_savepoint.html); explicit-autocommit handling follows [Python sqlite3 documentation](https://docs.python.org/3.12/library/sqlite3.html#transaction-control-via-the-autocommit-attribute).

Internal savepoints use operation-unique names, so a denied release cannot shadow a caller's known savepoint. Cleanup only targets a savepoint actually created by the operation. If an external authorizer denies cleanup as well, a nested savepoint may remain in the caller-owned transaction; the caller retains commit/rollback responsibility and the catalog does not bypass the authorizer or roll back the caller wholesale. Declared column types/nullability, primary-key order, required unique keys and non-partial lookup indexes are checked before writes. Index metadata uses [SQLite table-valued PRAGMAs](https://www.sqlite.org/pragma.html#pragma_functions), available since SQLite 3.16; this optional catalog is not qualified on older SQLite builds. These checks detect unsupported layouts, not malicious raw-owner modifications or all physical corruption.

## Validation And Remaining Gates

Use synthetic disposable stores. Check explicit preparation, immutable definitions/bindings, normalized indexed restrictions, unknown targets and mismatches, no original-content storage, no automatic schema/backfill, old reader/writer compatibility, schema/contract/mode refusal, missing-table/index refusal, malformed stored restrictions, failure/retry at DDL/term/commit stages, caller transaction/savepoint ownership, reopen, concurrent retries and process interruption. Preserve native content and `user_version` exactly. Verify tuple and sqlite3.Row connections without mutating their configuration. No provider, resolver, embedding, private source or live database is needed.

Persistent protected activation/downgrade handling, authenticated resolver/participant intersection, current-epoch checks, project-membership/provenance indexing, authorized candidate generation, derived-policy lifecycle and adapter parity remain unimplemented. No full A/B acceptance scenario or protected compatibility claim is passed by a prepared-catalog test. This candidate changes storage/API contracts and remains provisional for upstream review; no upstream changelog or version bump is made for this unreleased branch. The operator's parallel changelog records our changes and validation/publication/deployment state separately.
