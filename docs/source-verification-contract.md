# S2a: Explicit Bounded Source Verification

Status: provisional downstream increment on S1b `2f331cc7a0cbc7047319db11f9e831da95426a50`. Reuses RFC 0004's `ContentResolver.open` and S1's immutable source revisions. No upstream acceptance, protected authorization, automatic recall hydration, deployment or migration is claimed. S2's authorized expansion, persistent observations and full relocation lifecycle remain separate work.

## Interface And Trust Boundary

`verify_source_revision(store, revision_id, *, locator, resolver, max_bytes=67108864)` reads the exact registered revision, then streams the caller-selected location through the caller-supplied `ContentResolver`. Import from `mnemosyne.core.source_verification`. `store` is an existing `MediaStore`; no database is opened or schema created by the helper. Ordinary recall, `resolve_open`, resolver registration and legacy APIs are unchanged.

This is an explicit trusted-owner diagnostic, not a model-facing operation or an authorization boundary. The host must authorize the revision and locator before calling and supply a resolver that enforces its filesystem/network roots, redirects, timeouts and transport policy. No implicit registry lookup, file/HTTP opener, URI fallback, presign, provider, model or embedding is used. Resolver code and its resource limits are trusted. This helper neither authenticates a caller nor makes protected source access safe by itself; P4/S2 expansion must add the common authorization contract before exposing protected evidence.

The explicit locator may differ from the immutable revision's recorded location, allowing a relocated copy to be checked without changing revision or asset identity. Never derive a new identity merely from the new path or silently mutate the existing locator. SHA-256 is calculated from the actual bytes read to EOF; `head` hashes, ETags, HTTP not-modified responses, claimed byte lengths and URL equality cannot substitute for reading the representation. Only `original-bytes` is supported now; other representations remain explicitly unverified rather than hashing an arbitrary rendition as the original.

## Results, Bounds And Recovery

The frozen `SourceVerification` observation binds revision/asset, exact locator, representation, expected and observed SHA-256 and byte count, UTC attempt time, status and fixed reason code. Its representation omits identifiers, locators and digests; these remain sensitive metadata, not anonymization. Returned metadata is for the already-authorized caller, not a public log or denial channel. It contains no original bytes, excerpts or exception text. It is not a signed credential, persisted verification record, authorization grant or guarantee about a later reopen.

Statuses distinguish `verified`, `changed`, `missing`, `inaccessible`, `unavailable`, `unverified` and `limit_exceeded`. A missing revision does not call the resolver. An unavailable stream cannot be diagnosed as missing/offline without evidence; `None`, timeout and connection failure remain unavailable. Unsupported schemes/representations and malformed binary streams are unverified. Unexpected resolver exceptions are fixed-code failures, never a successful empty source. Database errors and cancellation propagate rather than becoming successful empty recall.

The byte budget is an integer in 0..1,073,741,824, default 64 MiB. Reads request at most 64 KiB, limited to the remaining budget plus one byte to distinguish exact-fit EOF from overflow. A known expected size above budget refuses before opening. No unbounded `read()` or whole-source buffer is used. A malicious resolver returning more than requested violates the trusted stream contract and refuses verification; the helper cannot undo allocations made inside arbitrary resolver code. Stream timeouts remain the resolver's responsibility, so a byte budget is not a wall-clock deadline.

Only complete EOF observations expose a digest; a prefix, read failure, over-budget source or failed close is not verified evidence. Hash mismatch or an expected-size mismatch yields `changed`, preserving the expected revision and recording the complete observed hash/size. Empty sources can verify against SHA-256 of empty bytes, including with a zero budget. The helper closes every acquired stream on success, failure or cancellation; it does not swallow `BaseException` cancellation. It writes no verification table, changes no asserted revision status and never commits or rolls back caller transactions. Hosts may retain the returned observation externally with their own access/retention policy; a durable in-engine journal requires a separate schema contract.

Verification describes one stream at one time. Source mutation, resolver replacement, a caller-owned stale SQLite snapshot and a later reopened stream can invalidate assumptions; verified bytes are not leased or returned for later consumption. No automatic retry, reindex, relocation update, derivative regeneration or policy change occurs. Reauthorizing and verifying the exact bytes consumed during future evidence expansion remains an explicit S2/P4 gate.
