# Scoped Profile Administration

This additive API builds on the explicit owner-only [profile history](host-configuration-authority.md). It can edit profiles in both profile-only and [registry-bearing configurations](host-authorization-registry.md), but cannot edit that registry. It does not authenticate a real CLI/Hermes/MCP transport, grant memory access, activate protected mode or change legacy behavior. All examples use disposable metadata, not an installed configuration loader. No original documents, model calls or private stores are involved.

## Trust And Separation

`ProfileAdministration(owner, authority_id=..., issuer=..., authenticate=...)` must be created by a trusted host. `authenticate(opaque_request)` must return a complete, current exact `AdministrationSnapshot` from an authenticated administrative session, not from tool arguments, a username, chat/persona labels or model claims. Constructing this record is not authentication. The callback and raw owner authority must not be available to ordinary tools; arbitrary same-owner code remains outside the library boundary. An unqualified host cannot expose this as a protected administration tool.

The snapshot contains an issuer, principal, canonical independent `separation_id`, pinned configuration authority, exact authorization revision, positive epoch, bounded explicit profile scope and capabilities. The trusted authority must map aliases/personas for the same administrative actor to the same separation identity. Merely assigning two usernames does not prove independent approval. Registration, authenticated identity mapping, restore freshness and an actual administrative UI/CLI remain separate required integrations.

The only admitted capabilities are `profiles:view`, `profiles:labels`, `profiles:policy` and `profiles:approve`. There is no wildcard, content-read, grant-edit, delegation, identity-mapping, approval-policy-edit, key-export or superuser capability. A configuration administrator receives no content permission from this API. A single operator may separately hold owner/data capabilities explicitly, but that is outside this scoped facade and must not be described as separation against that owner.

## Workflow

1. `view(request, profile_id)` returns only the explicitly scoped profile (or its absence) and the global configuration revision. It checks fresh authorization before reading owner metadata and again before returning it. Unrelated profile contents are not returned. The global revision discloses configuration change activity to an authorized administrator; this interface does not promise per-profile activity confidentiality or constant-time responses.
2. `preview(request, profile_id, replacement)` prepares a process-local immutable plan, not a database write. `replacement` is an exact `ProfileDefinition` or `None` for removal. A display-only change requires `profiles:view` plus `profiles:labels`; adding/removing a profile or changing any policy identity/version/ordered levels requires `profiles:view` plus `profiles:policy`. Existing profiles require an increasing profile version. Display labels cannot alter enforcement, but label accuracy is still an administrator responsibility.
3. A semantic `policy` plan additionally requires `approve(other_request, exact_plan)` by a current, scoped `profiles:view`/`profiles:approve` principal with a different principal and canonical separation identity, resolved at the same authority-wide authorization epoch/revision as the proposer. The opaque approval is tied to the exact plan object/digest and predecessor. The proposer cannot approve using an alias of the same actor. Labels-only plans do not accept an approval token.
4. `apply(request, exact_plan, approval=exact_approval)` rechecks proposer and approver claims and the predecessor. It preserves every other profile and uses the owner's existing stage/witness/finalize protocol. It admits fresh claims immediately before the first write and before each subsequent publication boundary, then rechecks before returning. A changed authorization snapshot, stale epoch/revision/scope, revoked approval, expired handle, foreign process/thread, reentrant call, copied/forged handle or changed predecessor refuses. No callbacks execute while an owner SQLite transaction is held.
5. `cancel(exact_plan)` discards that local pending handle without writing. It is not authority revocation. Up to 64 pending plans are admitted for a configurable 1-300 seconds (default 60); expiration is based on process monotonic time. Expired plans are removed on access. Plans/approvals are not serializable credentials or durable receipts and must not enter model history/logs.

Preview validates the candidate's structural bounds and current policy consistency. The owner still checks immutable historical profile/policy versions when staging, so preview is not a promise that a conflicting historical version can be committed. Creation of an empty authority and provisioning its first committed configuration remain explicit owner operations, not administrative auto-provisioning.

### Profiles With An Existing Registry

No new method, argument or capability is required. `view`, `preview`, `approve` and `apply` retain the same scoped workflow when the current owner snapshot contains a registry. Preview validates the complete candidate profile set against that exact registry. Apply preserves its canonical metadata unchanged in the same witnessed revision as the profile update; it never reconstructs grants from administrator claims or accepts a replacement registry. Even an empty registry remains a version-2 configuration rather than downgrading to legacy profile-only format.

Removing a profile referenced by a store, or removing a classification used by a conversation/grant, refuses at preview without a write. Removing an unused profile remains a semantic change requiring independent approval. Changing policy identity/version or ordered levels likewise requires independent approval, even if all existing classification names remain valid: reordering can change the meaning of existing ceilings. Display-only permission cannot authorize such a change.

Any intervening configuration publication, including a grant/route/identity change by the separately trusted owner, invalidates the preview; the facade cannot restore its prior registry. A successful profile edit advances the global configuration generation and invalidates existing request bindings, including for label-only edits. Obtain a fresh authenticated request handle; do not reuse old evidence or model context merely because grants were unchanged. This conservative global invalidation is intentional, not a per-profile optimization.

The trusted administrative authentication callback remains independent from registry content grants. Neither a registry entry nor permission to change display labels authenticates an administrator, and configuration capabilities do not grant data access. This facade exposes no principal, grant or route mutation; the separate [grant-only interface](host-grant-administration.md) has its own trusted claims, capabilities and approval exclusions. Principal/route administration remains unsupported. No new storage schema, migration, source retrieval, embedding call, regulatory evaluator or automatic host activation is introduced.

## Interruption And Recovery

The facade consumes a plan immediately before attempting the first write. On any uncertain write, inspect the durable owner receipt using `plan.operation_id` and the independent witness; do not retry `apply` or silently manufacture a new plan. Only the separately authorized owner recovery path can inspect/finalize uncertain publication. It does not exist as an administration capability here.

Revocation before witness advancement can leave an inert prepared record while the prior matching configuration remains current. Revocation after witness advancement can fence reads until explicit owner recovery. A final authorization/output failure can occur after the configuration committed; a refusal is not proof nothing changed. No automatic rollback, replay or unwitnessed advancement occurs. Existing owner recovery and surviving-anchor limitations still apply.

Checks define local admission, not a distributed atomic transaction with an external identity service. Revocation after a gate cannot retract already admitted local work. Correct epoch monotonicity, alias mapping, callback freshness and process isolation require a qualified host binding. The facade does not authorize changes to principal grants, routes, membership, domain evaluators or provider output; those paths remain unsupported rather than inheriting configuration capabilities.

## Qualification Boundary

Use synthetic authenticated-request fixtures to test scope denial before owner reads; independent approval; alias self-approval refusal; plan tampering/replay/expiration; stale proposer/approver revisions; concurrent configuration changes; interruption at each publication boundary; content-free public refusals; and absence of data-access/activation methods. Existing source/profile/witness tests remain applicable. Passing those fixtures does not establish actual transport authentication, regulatory compliance, all-path policy enforcement or production readiness.
