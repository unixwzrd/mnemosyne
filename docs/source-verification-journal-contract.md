# S2b: Durable Source Verification Observations

Status: provisional downstream increment on S2a `4a564f3fa00b0abbc852dd438766b78058cdedf9`. Adds an optional append-only metadata journal, not protected authorization, source expansion, a current-source oracle or deployment. S1 revision assertions and S2a byte-verification behavior remain unchanged. Upstream schema/API approval and version/changelog disposition remain separate submission gates.

## Interface And Meaning

`SourceVerificationJournal(store)` uses the supplied `MediaStore` connection without opening a database or creating schema. Import from `mnemosyne.core.source_verification_journal`. `record(observation, *, event_key, producer)` explicitly records one frozen S2a `SourceVerification`; `get(revision_id, *, event_key)` returns its immutable `VerificationRecord` or None; `list(revision_id, *, limit=100, offset=0)` returns a deterministic bounded page. Reading an absent optional journal does not migrate or write it.

This is a trusted-owner report journal. A Python dataclass, a producer label and matching checksums are not authentication or attestation that the caller really ran the verifier. Hosts must authorize access and retain actual verifier/artifact provenance separately. Recording a reported `verified` status never upgrades S1's `digest_status='asserted'`, grants access, proves source freshness or verifies bytes consumed during a later reopen. No automatic source fetch, resolver lookup, model, provider, embedding, reindex or protected activation is introduced.

An event is keyed by `(revision_id, event_key)` with a deterministic versioned SHA-256 event ID. `event_key` is a bounded opaque caller receipt/job key; `producer` is a bounded caller-reported implementation/artifact identity, not a secret, arbitrary report or source payload. Exact retries with the same observation and producer return unchanged; different immutable metadata conflicts. A fresh verification attempt needs a new event key even when the bytes match. After an uncertain commit, use `get` before retrying or refetching; do not silently replace the prior observation or invent an automatic retry.

## Validation And Storage

The explicit first record creates only `media_source_verification_events` and its revision-order index, atomically with the event. Known schema version 1, exact supported DDL/index and no journal triggers are required; existing unknown/partial shapes refuse without repair. No original bytes, excerpts, BLOBs or freeform metadata are stored. IDs, locators, digests and producer labels remain sensitive metadata and require controlled access. Records/receipts omit sensitive fields from repr; there is no automatic logging, export or retention sweep.

The trigger refusal includes both main-schema and connection-local TEMP triggers naming the journal table. A TEMP trigger can target a main table and still run on a main-qualified INSERT, as specified by [SQLite](https://www.sqlite.org/lang_createtrigger.html#temp_triggers_on_non_temp_tables). The guard conservatively refuses such configured connections rather than removing owner triggers or assuming main qualification prevents their side effects.

Validate exact observation type, bounded fields, canonical UTC attempt time, status/reason pairing, digest/count consistency and producer/event-key syntax before writing. Complete observations require full SHA-256 and size consistency: matching means verified, a mismatch means changed. Partial, unavailable, close-failed and over-budget outcomes must not carry a digest. Missing or malformed revision observations cannot create orphan history; source missing/inaccessible/unavailable results for a registered revision can be recorded. The main-schema revision must still match its asset, representation, asserted hash and expected size at recording time. Otherwise refuse rather than rewriting either record. No latest-source pointer, cryptographic signature or relocation update is inferred.

Events retain the locator checked, expected/observed digest and size, original UTC attempt time, database UTC recording time, event key, producer and revision/asset identifiers. The S2a observation does not contain the byte budget, resolver confinement proof or a wall-clock deadline; the journal does not invent them. Future exact-evidence expansion must authorize and verify the actual bytes it consumes, regardless of historical success. Historical records preserve their original snapshot; raw owner database mutation/deletion can invalidate provenance and is not prevented by this API.

## Transactions And Recovery

Method-owned writes acquire `BEGIN IMMEDIATE` before schema/source reads and use a unique savepoint. A successful write receipt reports `committed`. Existing caller transactions retain ownership and snapshots; nested success reports `pending`, not durable acceptance. Caller commit/rollback determines visibility. `get`/`list` read the connection's snapshot, which may include pending events; readback on that connection is not proof of durable commit. Reads use a caller-preserving snapshot and never fetch a source.

Releasing a method-owned outermost read savepoint closes that read transaction; no extra blanket commit/rollback is issued on a successful caller-owned read. This follows [SQLite savepoint semantics](https://www.sqlite.org/lang_savepoint.html). INSERT results are consumed before checking their affected-row count or releasing the write savepoint, including when the caller enables `count_changes`. Python's [Cursor.rowcount contract](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Cursor.rowcount) requires completion of result-producing statements. The journal does not change the caller's pragma setting.

Schema creation, validation, source matching, insert and postcondition checks are atomic. Failure or cancellation rolls back only owned work or the nested operation savepoint where cleanup is permitted. Caller savepoints, progress/authorization handlers and unrelated writes are never cleared or committed on its behalf. Persistent cancellation or denied cleanup can require connection-owner recovery; catastrophic SQLite failures can abort a transaction themselves. Independent connections, not concurrent users of one connection, are the supported concurrency boundary. Caller-owned stale snapshots and `BUSY_SNAPSHOT` remain explicit, not a lifecycle-revocation guarantee.

Record APIs append or return an exact prior event; no update/delete, implicit pruning, orphan cleanup, source-status mutation or migration of existing stores occurs. Normal reopening and old S1/S2a readers remain usable. P3 must later define retention, export/sync, provenance revocation and protected audit access across these records before any protected-mode claim.

## Acceptance

Use only disposable synthetic stores. Cover lazy schema, immutable retry/conflict, producer binding, all supported result statuses, malformed/forged-inconsistent reports, registered-source binding, stable relocation history, pagination, read-only reopen, missing schema, explicit autocommit modes, caller pending commit/rollback, competing connections, uncertain-commit recovery, mid-insert failure, process interruption, permission/cancellation/cleanup refusal, TEMP shadows and unknown schema/index/triggers. Inspect that original bytes are absent and S1 assertions/assets/moments remain unchanged. Qualify legacy reads, pinned package/interpreters, installed artifact and scoped review; no broad performance or protected readiness claim follows from a green journal suite.
