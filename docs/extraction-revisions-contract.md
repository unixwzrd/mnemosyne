# Extraction Revision Metadata: S1b Candidate

Status: provisional downstream contract, October 19, 2026, based on S1a `1ca1a038ae6faa6ee7cc3b2586df85378cd03340`. No upstream approval, publication, deployment or protected operation is claimed. This increment is independently reviewable against S1a; it is not an automatic correction or recall pipeline.

## Interface And Identity

`MediaStore.register_extraction_revision(source_revision_id, moment_id, *, revision_key, extractor, extractor_version, config_hash, output_hash, output_locator=None, predecessor_extraction_revision_id=None)` returns `ExtractionRevisionWrite(extraction_revision_id, status)` with `created` or `unchanged`. `get_extraction_revision(id)` returns metadata or `None`; `list_extraction_revisions(source_revision_id, moment_id, *, limit=100, offset=0)` returns deterministic bounded pages, with limit 1..1000. Missing optional schema returns empty reads without migration. No method selects a current, reviewed or accepted result.

Identity is SHA-256 of versioned JSON `["v1", source_revision_id, moment_id, revision_key]`, prefixed `extraction:sha256:`. The caller supplies a stable event key, not the output digest. Retrying the same event is idempotent; conflicting immutable metadata raises `ValueError`. Distinct events with equal outputs stay distinct and are not independent corroboration. Input/source bytes and extraction output have separate asserted digests. Extractor/version labels and the SHA-256 of its configuration record processing provenance; the exact configuration bytes are owned externally, not retained by this API. No digest is independently verified here.

The source revision and existing moment must belong to the same existing asset. The moment supplies the legacy span and speaker identity, not a claim that its text describes this byte revision. Registration of that relationship is a caller assertion; it does not infer evidence verification from the asset join. A correction explicitly names an earlier extraction of the same source revision and moment. Self-reference, unknown predecessors and cross-source/cross-span predecessors are refused. Branching is permitted; automatic reconciliation is not. Correcting speaker identity, splitting spans or linking processing across byte revisions needs a later explicit relationship contract and is not encoded by mutating old moment IDs.

## Storage And Compatibility

The optional `media_extraction_revisions` table stores ID, source revision, moment, event key, extractor/version, configuration/output digests, optional external output handle, predecessor, asserted-digest status and UTC registration time. Unique `(source_revision_id, moment_id, revision_key)` identity and the parent/time/ID index support bounded reads. There are no payload, transcript, excerpt, vector, arbitrary metadata or BLOB columns. Identifier and label strings have explicit bounds (256 for IDs/event keys, 128 for extractor/version); external handles are bounded to 4096 characters and reject controls and known inline/executable `data:`/`javascript:` schemes. This is not a complete resolver safety or aggregate retention-budget policy.

Schema is created only inside explicit registration, atomically with the new record. Transactions follow S1a: acquire `BEGIN IMMEDIATE` before schema access when owning the transaction, otherwise use a caller-preserving savepoint; finalize owned transactions with SQL COMMIT/ROLLBACK, including explicit-autocommit connections. No backfill, legacy-text overwrite, embedding, source fetch, provider call or alteration of legacy deduplication occurs. Existing source revisions, moments and working memories are unchanged. A legacy reader sees its original text; it must not be described as automatically correction-aware. Full correction-aware recall, stale-derivative handling and embeddings belong to later resolver/indexing work.

Raw database owners can bypass application-level integrity. Retention, export, deletion cascades, speaker correction, human review history, processing timestamps distinct from registration, policy inheritance and protected authorization are not implemented by this metadata slice. No protected activation, CLI, MCP or Hermes entry point is introduced. Upstream schema/API review and version/changelog decisions remain publication gates.

## Qualification

Use synthetic disposable stores only. Exercise same-span correction without legacy text replacement, event retries/conflicts, independent equal-output events, parent/predecessor validation, absence of payload and automatic schema creation, bounded reads, caller transaction ownership, injected failures/retry, independent-connection contention, old-reader compatibility, no IO/inference and supported interpreter transaction modes. These cases qualify the metadata contract, not all of A9 or B4 and not an end-to-end protected memory system.
