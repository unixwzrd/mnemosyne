# P2a: Explicit Bank-Level Authorized Reads

Status: provisional downstream implementation, dependent on P1a/P1b. This is not protected-mode activation, an upstream-approved API, or an enforcement retrofit for existing callers. Prepared stores remain readable by legacy APIs. No live store or adapter is migrated.

## Boundary And Trust

`PolicyReader(PolicyStore(connection), bank=..., verify_context=...)` is an explicit, read-only API over an existing prepared catalog. It requires SQLite 3.35 or newer. It never opens a default database, prepares schema, modifies content, fetches sources, calls embeddings or enables protection. Only `PolicySurface.DIRECT` is declared. BEAM, vector, lexical, graph, writes, derivatives, maintenance, export and adapters remain unqualified and are not exposed through this reader.

Every operation obtains the host-bound `AccessContext` and calls the required synchronous verifier as `verify_context(context, bank=bank, destination=destination)`. The trusted host must authenticate issuer and principals, intersect all participants' grants, check current context/policy epochs, and bind the actual receiving destination. It returns a `BankReadGrant` containing that context fingerprint, prepared domain, exact bank/destination, decision ID and allowed owner/tenant sets. Construction of either dataclass is not authentication. There is no built-in permissive verifier or model/tool argument accepting claims. Production transport integration remains P4 work; tests use a synthetic trusted registry only.

The context must explicitly select the configured bank, destination and `read:bank` operation, with `assurance="authenticated"`. Empty grant sets are never wildcards. P1b has no project-membership index: a nonempty project selection refuses as unsupported. An empty project selection alone grants nothing; the distinct bank-wide operation and verified bank-wide grant are both mandatory. All owner grants must be authorized for every participant; tenant membership is an additional restriction, not an owner bypass. A non-tenant record still requires an allowed owner.

The verifier runs once per operation, before the SQLite snapshot, with no cached decision. Exceptions become a content-free `context_unavailable` refusal rather than a successful empty result; explicit policy refusals remain refusals. Invalid verifier outputs or scope/fingerprint mismatches deny access. Asynchronous verifiers are unsupported. Freshness is checked at request start, not a promise of linearizable revocation during an in-flight read. Copied async contexts must still pass fresh verification on each call. P3/P4 must supply lifecycle-wide revocation and authenticated transports. A trusted in-process owner can bypass SQLite or forge any Python object and is outside this API's boundary.

## Selection Before Content

An indexed, metadata-only `AS MATERIALIZED` CTE selects bindings with the exact policy/version and classification rank at or below the context ceiling. It also requires an allowed owner, allowed tenant when present, at least one matching audience, the exact purpose, and every required compartment. Empty audience/purpose terms deny. Any overlay or unknown restriction dimension excludes the row rather than silently ignoring it. Unbound rows are excluded, not classified as public. Missing/incompatible catalogs or missing definitions refuse; no legacy fallback is attempted.

Only this authorized candidate relation is joined to the allowlisted native working, episodic or canonical table. Content is selected only by direct reads; candidate listing does not select it. All table references use `main`, values use parameters, and record kinds are enums, not SQL identifiers from users. The materialization fence relies on the documented [SQLite materialization behavior](https://www.sqlite.org/lang_with.html#materialization_hints); older engines refuse without fallback. This limits application-level materialization, not physical page access or a malicious database owner's ability to alter metadata. Valid catalog/native data is an owner-maintained prerequisite; this is not an arbitrary hostile-database parser.

`get(kind, record_id, destination=...)` returns `AuthorizedMemory` or `None`; denied and nonexistent identities are indistinguishable. `candidate_ids(kind, destination=..., limit=100, offset=0)` returns authorized provenance without content. Limits are 1..1000; offsets are bounded nonnegative integers. Authorization and native-parent existence precede pagination, so denied and orphaned rows do not consume the page. Native IDs provide stable ordering; there is no search-score or recall-ranking claim. Combined owner, tenant, audience and compartment labels are bounded at 900 to fit SQLite's historical parameter limit without truncation.

Each returned record identifies its kind, native ID, bank, policy binding/version/classification and the verifying decision/context/epoch. Representations and fixed refusal messages omit content and denied identities. SQL/database errors propagate rather than becoming empty success; callers must not expose raw infrastructure errors to untrusted channels. Reads share one caller-safe SQLite snapshot for catalog checks, definitions and candidate/content selection, without committing or rolling back caller-owned changes. Callers must supply an exclusively used connection during an operation; cross-thread use of one SQLite connection is not synchronized here.

## Acceptance And Remaining Work

Synthetic tests must exercise every restriction, ambiguous empty scopes, verifier failures/freshness, native IDs, bound parameters, denied-content materialization, candidate starvation, schema refusal, snapshot consistency, transaction ownership and A/B/A interleaving. Compare this increment to its accepted P1b base for unchanged legacy behavior, and separately report authorized candidate quality and bounded read latency. No formal overhead budget is established by a legacy benchmark.

This is P2a, not completion of P2 or scenarios A1-A18/B1-B10. Project-indexed selection, existing BEAM/vector/lexical/graph integration, protected writes and store-wide incompatible-client refusal remain required. P3 covers inheritance/revocation/cache/maintenance/export; P4 covers parity and activation. Source revision/expansion work remains on its separate S branch. No release bump or upstream changelog modification is made during provisional downstream development; contributor versioning remains a publication gate.
