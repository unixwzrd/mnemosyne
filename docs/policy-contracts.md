# Optional Policy Contracts: P1a Candidate

Status: provisional downstream contract, October 19, 2026, based directly on upstream `4e565333a3549b75fae7b9ae814b25b152a2453e`, independent of S1. No upstream architecture approval, activation, enforcement, migration, release or deployment is claimed. This is the first P1 slice; indexed bindings and persistent activation/downgrade contracts are P1b, not implemented here.

## Types And Compatibility

`core.policy` contains frozen, bounded, stdlib-only records. `PolicyDefinition(policy_id, version, levels)` defines a deployment's ordered vocabulary, lowest first; there is no government taxonomy or default policy. `AccessContext` holds host-resolved context/epoch, policy identity/version, issuer/platform, effective authenticated principal set, classification ceiling, purpose, asserted authentication-assurance label, bank/project/compartment/audience/operation/destination sets and optional channel/conversation IDs. Mutable collection inputs are copied into immutable collections. Unknown participants and participant intersection must be resolved by the host before constructing a context; the type cannot authenticate its creator, validate an assurance assertion or current registry epoch, or constrain an owner with direct Python/SQLite/filesystem access.

`AccessContext.narrow(banks=..., projects=..., operations=..., destinations=...)` accepts exact subsets only. Omitted/None selection preserves the host's effective grants; an explicit empty collection selects none. Unknown or malformed selections refuse with a content-free reason; there is no wildcard, guessed bank/project, empty-to-all fallback or privilege-raising selector. Principals, compartments, purpose, policy and epoch cannot be changed through selection. Operation/destination labels are opaque exact-match grants; any future adapter must interpret supported operations explicitly, never treat an unknown label as permission. This is request scoping, not row authorization.

`MemoryPolicy` holds proposed classification/restriction metadata: policy/version, classification, owner, classification source, compartments, audiences, purposes, overlays, optional tenant and paired origin context/epoch. Context-derived classification requires an origin. These are not JSON blobs written into a live store; no schema or record binding is created. Policy vocabulary validation checks identities/versions/classification labels only, not access, consent, overlay semantics, authorization freshness or source authenticity. Unsupported restrictions must not be silently discarded by later enforcement. Empty restriction-set semantics require P1b/P2's reviewed row contract; do not infer allow-all from an empty value here.

`AdapterCapabilities` uses explicit `PolicySurface` members and contract version 1. Its default declaration is empty; `require` refuses an unknown or undeclared surface. No existing core/Hermes/MCP/CLI adapter is declared protected-capable by this increment. A declaration is not proof or a security certificate. Enabled paths require P2/P3 acceptance before P4 exposes activation; unsupported paths must then refuse before data access or mutation. This increment does not install such guards into existing paths.

## Trusted Runtime Boundary

`runtime_context.bind_access_context(context)` is a scoped in-process host seam accepting only `AccessContext` or explicit None, not dictionaries. It restores the previous binding on success or exception. `get_access_context()` defaults to None, independent of existing request-token attribution; `get_access_context(required=True)` refuses if missing. Existing token-name getters/setters and all retrieval/write signatures retain their behavior. Policy imports are lazy inside the new optional calls, so importing/using legacy runtime context does not load the policy/core modules or add their import cost. There is no context factory taking model-provided tool arguments, no automatic promotion of an authenticated token name into grants, and no change to tool schemas or an authentication service.

This is not protection against trusted host code constructing arbitrary claims: the future adapter must authenticate/resolve them, enforce participant intersections and maintain policy/epoch validity. Python context-local state is not a cryptographic capability. Task/thread propagation must be explicit in each host dispatch seam; no automatic wrapper of executors or detached tasks is installed here. Child tasks can retain a copied snapshot beyond the parent's scoped binding; reauthorization/lifetime handling belongs to P2/P4 and cannot rely on restoring the parent alone. Qualification uses explicit empty/copy contexts rather than platform-dependent thread inheritance defaults. The implementation uses token set/reset in try/finally, compatible with Python 3.10+, not the token context-manager shorthand added in Python 3.14. See [Python contextvars documentation](https://docs.python.org/3/library/contextvars.html).

`AccessContext.fingerprint()` deterministically includes all fields plus contract version, sorting sets. It is a cache-key ingredient, not authorization, encryption or anonymization; future cache keys must additionally bind memory/source revisions and a current authorization decision. Default record repr omits field contents. `PolicyRefusal` carries a fixed reason (`missing_context`, `policy_mismatch`, `invalid_selection`, `unsupported_surface`) without denied identifiers or supplied values. No contentful audit log is added.

## Acceptance And Remaining Work

Use synthetic contexts and disposable stores. Check normalization/immutability/bounds, custom vocabulary, policy mismatches, narrowing/empty semantics, fingerprint sensitivity, dictionary refusal, exception restoration, nested calls, A/B/A async overlap, task snapshot lifetime, explicit empty/copied thread contexts, unchanged token attribution and unchanged legacy memory paths. No embedding/provider calls or live stores are needed.

P1b must define additive first-class indexed policy bindings, persistent protected-domain records, interruption/recovery and incompatible-client refusal before any activation can be offered. Legacy rows in a future protected domain require an explicit eligibility contract. P2 supplies authorized candidate generation and direct reads/writes; P3 covers lifecycle/derivatives/caches/export; P4 qualifies host adapters and activation. A test of these types does not pass B7/B8 or establish fail-closed retrieval. Upstream version/changelog handling remains a publication decision; downstream changes are recorded in the separate operations contribution changelog.
